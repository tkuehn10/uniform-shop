# Uniform Shop Stock System — Requirements Document

**Version:** 0.8 (draft)
**Date:** 12 September 2026
**Prepared for:** The uniform shop stock management project

## 1. Purpose

This document defines the requirements for a simple stock inventory system for a small school uniform shop. It covers receiving stock from supplier orders, recording sales, performing stocktakes, reporting on sales over time, and a simple volunteer roster for shop opening times.

## 3. Users and roles

Two roles, each with their own login:

| Role                   | Can do                                                                                                                                                                                                                                                                            |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Admin**              | Everything a User can do, plus: create/edit/archive items and sizes, enter initial or corrected stock levels, create and manage supplier orders, check in deliveries, perform stocktakes, view all reports, configure the weekly opening-times pattern and school holiday periods |
| **User** (sales staff) | Record sales, view current stock levels and item/size availability, view the roster calendar and claim/un-claim opening-time slots. Cannot create orders, check in deliveries, or perform stocktakes                                                                              |

Each login is tied to an individual staff member (not shared), so actions (sales, stocktakes, deliveries) can be attributed to whoever performed them.

## 4. Core data model (conceptual)

- **Item** — a uniform product, e.g. "Boys Short Sleeve Shirt". Has a name, an optional photo, and optionally a category (shirts, shorts, jumpers, hats, etc.) and a price (for reference, not for payment processing). Can be archived without being deleted (see REQ-36/37).
- **Size** — each item has a defined set of sizes it comes in (e.g. 4, 6, 8, 10, 12, S, M, L, XL). Stock is tracked per item **and** size combination (e.g. "Boys Shirt, Size 10" is tracked separately from "Boys Shirt, Size 12"). A size can also be archived independently of the rest of its item.
- **Stock level** — current on-hand quantity for each item/size combination, changed by deliveries, sales, stocktake reconciliations, and manual adjustments (including initial setup).
- **Supplier order** — a purchase order placed with a supplier, with a supplier name, an order number, an order date, and one or more line items (item, size, quantity ordered). Progresses through a fixed sequence of statuses (see REQ-6).
- **Supplier** — a supplier name; the system remembers every supplier name ever used so it can be picked again on future orders rather than retyped.
- **Delivery** — a record of stock received against a supplier order, on a given date. A supplier order can have multiple deliveries (partial shipments) until fully received.
- **Stocktake** — a point-in-time count of on-hand stock for some or all item/size combinations, on a given date.
- **Sale** — a transaction recording one or more items/sizes and quantities leaving stock, with a date/time and which User recorded it.
- **Opening-time slot** — a recurring weekly shop-opening period (day of week, start time, end time), set up by Admin and repeating every week.
- **Roster claim** — a name attached to one date's occurrence of an opening-time slot, meaning that person is rostered on for the shop at that time.
- **School holiday period** — a date range (with an optional label, e.g. "Term 3 holidays") during which the shop is assumed closed, set up by Admin.

## 5. Functional requirements

### 5.1 Item management

- **REQ-1:** Admin can create and edit items, including their name, category, sizes offered, and a photo. A photo can be uploaded, replaced, or removed at any time.
- **REQ-2:** The item's photo is shown alongside the item wherever it appears in the system (stock view, sales screen, order screens) so staff can visually confirm they've picked the right item.

### 5.2 Supplier orders and delivery check-in

- **REQ-3:** Admin can create a supplier order by entering: a supplier name (typed with autocomplete suggestions drawn from previously used suppliers, or entered fresh for a new supplier), an order number, an order date, and one or more line items (item, size, and quantity ordered).
- **REQ-4:** The system remembers every supplier name ever entered and offers it as a suggestion when starting future orders, so it doesn't need to be retyped exactly.
- **REQ-5:** Admin can view a list of all supplier orders, showing order number, supplier name, order date, and current status.
- **REQ-6:** Each supplier order moves through a fixed, linear sequence of statuses, in order:
  1. **Order Placed** — order created and sent to the supplier
  2. **Partially Received** / **Fully Received** — at least one delivery has been checked in; this sub-status reflects whether all ordered quantities have arrived yet
  3. **Invoice Checked** — received stock has been counted and reconciled against the supplier's invoice
  4. **Invoice Sent to Treasurer** — invoice forwarded on for payment
  5. **Closed** — order fully complete

  Normally, an order advances through these stages only via the actions in REQ-7, REQ-10, REQ-11 and REQ-12 below, in order. Admin can also manually override an order to any stage directly (REQ-13) when the normal flow doesn't fit.

- **REQ-7:** When a delivery arrives, Admin can check in stock against the relevant order, entering the quantity received for each item/size. This increases the on-hand stock level for that item/size immediately, and moves the order to "Partially Received" or "Fully Received" depending on whether every line is now fully received.
- **REQ-8:** A supplier order can be checked in across multiple deliveries; the system tracks quantity received vs. quantity ordered per line, and shows what remains outstanding.
- **REQ-9:** Admin can view the delivery history for a given order (each delivery's date and what was received), and a shop-wide delivery history across all orders.
- **REQ-10:** Once stock has been received, Admin can mark the order as "Invoice Checked", confirming the received quantities have been compared against the supplier's invoice, with an optional note to record any discrepancy found.
- **REQ-11:** Admin can mark the order as "Invoice Sent to Treasurer", recording the date the invoice was forwarded for payment.
- **REQ-12:** Admin can close an order once the invoice has been sent to the treasurer.
- **REQ-13:** Admin can manually override an order's status to any stage in the sequence — including jumping ahead or moving it back — for cases the normal flow doesn't cover (e.g. closing early because a discontinued item will never be fully received or invoiced, or correcting a mistaken status change).

### 5.3 Stock viewing

- **REQ-14:** Both Admin and User can view current on-hand stock, broken down by item and size.

### 5.4 Stocktake

- **REQ-15:** Admin can start a stocktake on a given date and enter counted quantities for each item/size. Stocktakes can be a full count (all items) or a **spot stocktake** covering just a chosen subset of items/sizes.
- **REQ-16:** For each item/size counted, the system calculates the expected quantity (previous stocktake baseline + stock received since − sales recorded since) and compares it to the counted quantity.
- **REQ-17:** The difference between expected and counted quantity is treated as "sold since last stocktake" for that item/size, and is used to true-up the system's on-hand stock to match the physical count.
- **REQ-18:** Admin can view past stocktakes, including the date, counted quantities, and the calculated sold/adjustment figures at the time.

### 5.5 Sales reporting

- **REQ-19:** Both Admin and User can view how many units of each item/size were sold within a selected period.
- **REQ-20:** The period can be a custom date range, or a quick preset (e.g. this month, this term — manually dated, this year).
- **REQ-21:** Sales reports can be viewed for a single item/size or summarized across all items.
- **REQ-22:** Sales reports (and stock/order/delivery lists, where useful) can be exported as CSV.

### 5.6 Recording a sale

- **REQ-23:** A User (or Admin) can record a sale by selecting one or more items/sizes and quantities. No payment or price handling is required — recording a sale simply decreases on-hand stock and logs the transaction (item, size, quantity, date/time, staff member).
- **REQ-24:** If a sale would take an item/size's stock below zero, the system shows a warning but still allows the sale to be recorded (not a hard block) — stock can go negative to reflect real-world situations like selling from a delivery not yet checked in.

### 5.7 Roster

- **REQ-25:** Admin can set up the shop's recurring weekly opening times (e.g. Tuesday 8:30–9:30am, Thursday 3:00–4:00pm), which then repeat automatically every week.
- **REQ-26:** Any logged-in user (Admin or User) can view a calendar of upcoming opening-time slots, showing which are claimed (and by whom) and which are still open.
- **REQ-27:** Any logged-in user can claim an open slot on a given date by entering a name; the slot then shows that name as rostered on.
- **REQ-28:** Any logged-in user can un-claim a slot (remove the name), freeing it up for someone else to claim.
- **REQ-29:** Admin can edit or remove the recurring opening-times pattern (e.g. shop hours change); this updates future, not-yet-claimed occurrences going forward.
- **REQ-30:** Admin can define school holiday periods (a start date, an end date, and an optional label such as "Term 3 holidays").
- **REQ-31:** The calendar visually marks any dates that fall within a defined school holiday period, so it's obvious at a glance the shop is closed then.
- **REQ-32:** No opening-time slots are generated or shown as claimable on dates within a school holiday period.
- **REQ-33:** Admin can edit or delete a school holiday period (e.g. dates change); this recalculates which opening-time slots are suppressed.

### 5.8 Initial setup, stock corrections, and archiving

- **REQ-34:** Admin can enter starting on-hand stock quantities for every item/size in one bulk-entry screen (rather than one at a time), for setting up the system with the shop's existing stock. This is recorded as a manual stock adjustment, not a sale or a stocktake discrepancy.
- **REQ-35:** Admin can manually adjust an item/size's on-hand quantity at any time (up or down), with a required note explaining why, to correct errors outside the normal delivery/sale/stocktake flows.
- **REQ-36:** Admin can archive an item, or an individual size within an item, removing it from the pickers used for sales, orders, and stock browsing day-to-day — without deleting it or any historical data that references it (past orders, deliveries, stocktakes, and sales stay intact and reportable).
- **REQ-37:** Admin can restore (un-archive) a previously archived item or size, making it available again in day-to-day pickers.

## 6. Non-functional notes

- Small-scale system: expected to be used by a handful of staff, single shop location, item catalog in the tens to low hundreds of item/size combinations.
- No payment processing, no integration with POS or accounting systems in this version.
- Data should be retained indefinitely for historical reporting (orders, deliveries, stocktakes, sales all timestamped and kept, not purged).

## 7. Out of scope (v1)

- Low-stock alerts / reorder point notifications
- Customer pre-orders (this system models supplier restocking only, not customer-placed orders)
- Payment processing or pricing/invoicing
- Multi-location / multi-shop support
- Roster notifications/reminders (e.g. emailing someone ahead of their shift)
- One-off, unplanned closures that aren't entered as a school holiday period (e.g. a sudden unplanned closure) — Admin can cover most cases, including single public holidays, by adding a holiday period for that date range (see A13)
